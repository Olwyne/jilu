## 1. Failles de sécurité

### Haute

| # | Problème | Où | Détail / correctif |
|---|---|---|---|
| S1 | **L'e-mail est lisible publiquement** | `firestore.rules` (`users/{uid}` : `allow read: if resource.data.settings.publicProfile == true`, sans auth) + `EditProfileModal` / `App.jsx:255` qui stockent `profile.email` | Tout le document `users/{uid}` est lisible par n'importe qui (même non connecté) dès que le profil est public : e-mail, `feedbackTimestamps`, `settings`, `reviews`, `feed`… Une requête `where settings.publicProfile == true` permet même de les énumérer. **Correctif** : ne pas stocker l'e-mail dans Firestore (il est déjà dans Firebase Auth) ; séparer un document `publicProfiles/{uid}` (handle, nom, avatar, stats) du document privé `users/{uid}`. |
| S2 | **Détournement de pseudo** | `firestore.rules` `pseudos/{handle}` : `allow write: if request.resource.data.uid == request.auth.uid` | N'importe quel utilisateur connecté peut écraser `pseudos/xxx` avec son propre uid et prendre le pseudo de quelqu'un d'autre (`/u/xxx` pointe alors vers lui). La vérification « pseudo pris » n'existe que côté client. **Correctif** : `allow create: if … && !exists(...)`, `allow update: if false`, `allow delete: if resource.data.uid == request.auth.uid`, valider le format (`^[a-z0-9_]{2,20}$`) et la clé du document. |
| S3 | **La suppression de compte ne supprime pas les données** *(déduit)* | `AccountView.jsx:~199` | `deleteAccount()` supprime l'utilisateur Auth **avant** de supprimer les documents Firestore. Une fois l'utilisateur supprimé, `request.auth` est nul, donc les règles refusent les `deleteDoc` suivants : `works`, `watched`, `reviews`, `users/{uid}` restent. Les pseudos, `follows` et scores du quiz ne sont de toute façon jamais supprimés. Problème RGPD (la page de confidentialité promet probablement l'effacement) + pseudos bloqués à vie. **Correctif** : supprimer les données d'abord (puis Auth), ou mieux une Cloud Function/extension « Delete User Data ». |
| S4 | **Proxys API ouverts, sans quota** | `api/*.js` | Aucune authentification ni limitation de débit : n'importe qui peut consommer vos quotas TMDB/RAWG/Google Books/Spotify. `api/tmdb.js` accepte un `path` arbitraire. `{ api_key, ...params }` laisse le client écraser la clé. `api/spotify-token.js` distribue un token à tout le monde. Les messages d'erreur internes sont renvoyés. **Correctif** : liste blanche de chemins, vérification du token Firebase (ID token) côté fonction, rate-limit (Vercel/Upstash), cache `Cache-Control` / `s-maxage`, `...params` avant la clé. |

## 3. Modèle de données, montée en charge, limites d'API

### Constat sur le modèle actuel
Chaque utilisateur possède **sa propre copie complète de chaque œuvre**, y compris `seasons[].episodes[]` (titres, dates de diffusion) :

```
users/{uid}                      ratings, reviews[], feed[], games, favorites, ccLikes, settings, profile  (1 gros document)
users/{uid}/works/{workId}       métadonnées + saisons/épisodes complets  (dupliqué pour chaque utilisateur)
users/{uid}/watched/{workId}     { eps: { "s-e": timestamp } }
reviews/{id}                     avis communautaires (déjà au bon endroit)
```

Conséquences :
1. **Duplication** : 1 000 utilisateurs suivant *Breaking Bad* = 1 000 copies de ses ~60 épisodes. Pour *One Piece*/un manga, une seule copie pèse déjà lourd.
2. **Rafraîchissement par client** : à chaque ouverture, `refreshStaleWorks(DAY, 100)` interroge TMDB/AniList/MangaDex pour jusqu'à 100 œuvres (une œuvre TV = 1 + nb de saisons + 2 appels ; un anime ajoute AniList), puis toutes les heures. Avec N utilisateurs on refait N fois la même requête.
   - TMDB et MangaDex passent par vos fonctions Vercel : **une seule IP/clé partagée pour tous** → quotas partagés. MangaDex en particulier est très restrictif (≈ 5 req/s par IP).
   - AniList est appelé directement depuis le navigateur (~90 req/min par IP) → erreurs 429 silencieuses pour les grosses bibliothèques.
3. **Lectures Firestore** : à chaque ouverture, trois `onSnapshot` lisent *toute* la collection `works` + *toute* la collection `watched` (≈ 2 × nb d'œuvres lectures par session), sans cache persistant. Le quota gratuit est de 50 000 lectures/jour : avec 300 œuvres par utilisateur, une cinquantaine de sessions/jour suffisent à le dépasser. S'ajoutent le fil d'amis (1 lecture de document utilisateur complet par ami suivi à chaque montage) et le `get()` des règles.
4. **Documents qui grossissent sans limite** : `reviews[]`, `feed[]`, `games`, `ratings`, `ccLikes` vivent dans `users/{uid}` (limite Firestore : 1 Mo par document, et chaque modification réécrit les tableaux entiers).
5. Les avis communautaires (`reviews`) ne sont pas dupliqués : bon point, à conserver.

### Le modèle est-il adapté à « plus d'utilisateurs » ? Non, pas en l'état.
Recommandation : **une collection de catalogue partagée** + des documents utilisateur légers.

```
catalog/{source}-{sourceId}      title(s), posters, category, genre, year, ended,
                                 seasons[] (ou sous-collection si volumineux), updatedAt
users/{uid}/library/{workId}     status, added, finishedAt, rating, favorite,
                                 eps: { "s-e": ts }              ← fusion works + watched
                                 + champs dénormalisés légers (title, poster, category)
users/{uid}/…                    settings, goals, profile privé
publicProfiles/{uid}             handle, nom, avatar, compteurs (lisible publiquement, sans e-mail)
reviews/{id}                     inchangé (+ règles de validation)
```

Ce que cela apporte :
- **Une seule copie par série**, mise à jour **une fois** pour tous. Le rafraîchissement passe côté serveur (cron Vercel ou Cloud Function planifiée) et ne vise que les œuvres encore en cours de diffusion (`ended === false`) ; les clients ne font plus que lire `catalog/*`. Fin du problème de quotas TMDB/AniList/MangaDex (≈ nb d'œuvres distinctes, pas nb d'utilisateurs × œuvres).
- **Moitié moins de lectures** en fusionnant `works` + `watched` en un document par œuvre ; en dénormalisant titre/affiche dans `library`, la bibliothèque s'affiche sans lire le catalogue (les saisons ne sont chargées qu'à l'ouverture d'une fiche ou pour le calendrier). Activer `persistentLocalCache` (IndexedDB) pour que les ouvertures suivantes ne relisent pas tout. Éviter le `get()` dans les règles grâce à `publicProfiles` séparé.
- Écrasements entre appareils réduits : un document par œuvre, mises à jour ciblées (`updateDoc(… 'eps.1-3': ts)`) au lieu de réécrire la map complète.
- `catalog` : lecture publique/authentifiée, écriture réservée au backend (Admin SDK) → les utilisateurs ne peuvent plus injecter de métadonnées arbitraires.

### Plan de migration proposé (sans casser la prod)
1. **Environnement séparé** : projet Firebase de test ou émulateur Firestore ; aucune écriture sur la prod pendant le développement. La branche reste locale tant que vous ne demandez pas de push.
2. **Phase 0 – règles & correctifs sûrs** (S1–S5, B1, B3) : indépendants de la migration.
3. **Phase 1 – lecture double** : ajouter `catalog` + `library` ; le code lit le nouveau modèle et retombe sur l'ancien si absent.
4. **Phase 2 – script de migration** (Admin SDK, idempotent, reprenable) : pour chaque `users/*/works/*`, créer/fusionner `catalog/{id}` (garder la version la plus récente, par `updatedAt`/nombre d'épisodes) puis écrire `library/{id}` (statut + `eps` de `watched`). Ne rien supprimer à ce stade.
5. **Phase 3 – double écriture** puis bascule des lectures ; vérification (comptage d'œuvres/épisodes avant/après par utilisateur).
6. **Phase 4 – nettoyage** (suppression de l'ancien modèle) seulement après plusieurs jours sans incident, avec export de sauvegarde préalable.
7. Mettre en place le **rafraîchissement serveur** du catalogue et supprimer `refreshStaleWorks` côté client.

## 4. Améliorations & fonctionnalités à ajouter

**Qualité / maintenance**
- Un seul gestionnaire de paquets, lockfile synchronisé, CI qui exécute `lint`, `test`, `build`, `audit`.
- Corriger/mocker `firebase.js` dans les tests, réparer les 8 tests en échec.
- Retirer du dépôt `Application web de suivi culturel-handoff.zip` et `extracted/` (≈ 1,6 Mo d'artefacts de design, le `.gitignore` exclut pourtant `*.zip`).
- README obsolète (React 18, `npm run test:run` inexistant, « l'utilisateur ne lit que son document `users/{uid}` » alors que les règles autorisent aussi les profils publics).
- i18n incomplet : chaînes en dur (`ReviewFeed`, `window.confirm`, messages de refresh).
- Accessibilité : nombreux `<div onClick>` à remplacer par des `<button>` (clavier/lecteurs d'écran).
- Cache service worker : les règles Workbox visent `api.themoviedb.org` alors que l'app appelle `/api/tmdb` → jamais appliquées.
- Spotify : un token demandé à chaque appel (pas de cache), détail d'artiste = 1 requête par album en série.

**Fonctionnalités pertinentes**
- Pagination/limitation du fil d'amis ; notifications serveur pour les nouveaux épisodes (le catalogue partagé le permet).
- Signalement/modération des avis publics (obligatoire dès qu'il y a plus d'utilisateurs).
- Export complet RGPD cohérent avec la suppression de compte.
- Surveillance : quotas Firebase/Vercel/TMDB, alertes de budget.
